## Phase 2 · SP3a — what shipped
Pure, DI'd `src/lib/solver/` module. `solve(build, ctx, options?) → SolveResult` where `ctx = { lookup, indexes }` (the existing `@/lib/types` dataset `Indexes` — NOT a new type), `options = { beamWidth?=16, topN?=5, statFit?, bound? }`. Unified **add-one-element beam search** over two open dimensions (subclass fragments + artifact perks): state = partial `Build`; a move adds one fragment (gated by the aspect-granted slot cap) or one artifact perk (gated by SP2 `canAddArtifactPerk`). States pruned by `state.priority` = **`synergyUpperBound`** (admissible optimistic bound, tie-break `priority || realized.score || key`); only **terminal (fully-filled)** states are completion candidates, ranked by realized `scoreSynergy.score + statFit`, top-N returned. `feasible=false` (empty builds) when pinned inputs admit no completion.

Key design points (verified in final review):
- **`synergyUpperBound` lives in `@/lib/synergy` (`bound.ts`), not the solver** — it co-varies with `scoreSynergy`'s weighting (which the seam hides), so the Phase-3 embedding layer stays drop-in. Solver reaches synergy ONLY via `scoreSynergy`/`getSynergies`/`synergyUpperBound`. Admissible per-keyword: `min(P,C)` links × triangular-rank × `ELEMENT_ALIGNED_MULT`, trigger cap, overlay clamped `Math.max(0,·)`. Independently verified to dominate the real (non-monotonic) scorer.
- **Prune key is the single admissible upper bound, NOT `realized + separate-gain`** — the split form is unsound because `scoreSynergy` is non-monotonic (a low-hash unaligned producer can steal a consumer from an aligned one).
- **Terminal-only routing is correct here because fill-to-cap is a HARD game floor** (Phase-1 decision: "fragments = max", "artifact tiers filled to slots" → underfilled builds are invalid deliverables). The admissible bound (computed fresh, not incrementally) still retains the path to the best *filled* build. **SP3b must revisit this if dynamic caps ever allow underfill.**
- **Acceptance gate (the point of the slice):** `tests/solver/beam.test.ts` delayed-reward test — a producer fragment (hash 200) whose only consumers are artifact perks survives the beam at W=1 with the bound ON (top build score 2, contains 200) and is pruned with a zero bound (top build 201, score 1.5). Proves the bound is load-bearing.

Parked follow-ups (non-blocking): tighten the bound for beam efficiency (measured vs real builds); revisit W=16 / topN=5 defaults; incrementalize per-successor recomputation in `makeState` (flagged in code for SP3b); DRY the key-comparator repeated across `beamSearch`/`solve`; author `CURATED_OVERLAY` entries (bound already guards negative weights).

## Decisions resolved (do not relitigate)
- **Plug synergy resolves by HASH via the side table; the NAME bridge is now only a fallback (slice 2a).** Option A landed with the re-ingest: `data/plug-tags.json` maps plug hash → `KeywordTags`. *Why a side table and not `WeaponPerk.tags`:* 112,486 plug entries vs ~1,057 distinct hashes ⇒ ~7.08MB inline vs 20KB keyed. Supersedes the slice-1 follow-up below.
- **Plug elements dedup at synergy-EFFECT granularity, not plug granularity (CONFIRMED by user during the slice-2a review).** Two weapons rolling the same perk = **one** producer. Both `collectBuildElements` and `deriveWeaponSlotReach` use `bridged?.hash ?? plugHash`. *Why:* keeping them identical is what preserves the admissible bound (realized must never exceed the bound) and slice-1 scoring semantics; per-plug keying costs 6× beam work (11,190 → 66,071 bound calls). The alternative — counting each instance — was considered and deferred: it requires pairing with the parked "tighten the bound" follow-up.
- **`championStuns` is COVERAGE, never a chain (slice 2a).** It is a separate optional field on `KeywordTags`, read nowhere in `src/`, and the scorer names `produces`/`consumes`/`triggers` explicitly rather than iterating tag fields. *Why:* a second anti-barrier source adds nothing, so it must never reach the depth-rewarding chain scorer. Verified on real data: 176 perks gained the field while **zero** perks changed `produces`/`consumes`/`triggers`, and no champion keyword appears in any entity's producer/consumer lists.
- **SP3b slice-1 (weapons) shipped** the runtime plug-NAME synergy bridge (Option B):
  `Lookup.perkByName` + `collectBuildElements` name fallback. Weapon plug hashes are a
  disjoint namespace from `perks.json`, so roll synergy resolves by plug NAME to a tagged
  sandbox `Perk`. FOLLOW-UP (Option A, deferred): tag weapon plugs at ingest in
  `scripts/ingest/transform.ts` (mirror the aspect/fragment `tags: tag({ text: itemText(...) })`

  landed, plugs carry hash tags and the name bridge degrades to a harmless fallback.
- **SP3a optimistic bound lives IN `@/lib/synergy` (`synergyUpperBound`), not the solver (CONFIRMED by user this session).** *Why:* an admissible bound needs `scoreSynergy`'s weighting internals, which the seam hides; colocating it with the scorer keeps the Phase-3 embedding layer drop-in (embeddings supply their own bound). Prune key is the *single* admissible upper bound, not `realized + separate-gain` (the split is unsound: `scoreSynergy` is non-monotonic under adding elements).
- **SP3a beam returns only terminal (fully-filled) builds; ranks by realized synergy.** *Why:* the Phase-1 game floors make fill-to-cap a hard requirement (underfilled builds are invalid deliverables), so terminal-only routing is correct despite `scoreSynergy` non-monotonicity; the admissible bound still retains the best *filled* build. **SP3b's dynamic caps (solver-chosen aspects) must revisit this** — if underfill becomes legal, terminal-only would need best-partial tracking.
- **SP3 is sliced; SP3a = fragments + artifact perks.** *Why:* the dominant risk is beam-search-vs-pairwise-synergy (delayed reward). A slice of two *synergy-coupled* subset-dimensions forces the beam to solve delayed reward on a small surface, before scaling all dimensions in SP3b. Not one independent-dimension pair (proves only plumbing), not one dimension (cross-dim synergy never appears).
- **SP3a partial scoring = optimistic completion bound (admissible upper bound).** *Why:* principled fix for delayed reward — never prunes a producer whose consumer could still come; it is the mechanism SP3b scales. Chosen over a crude tunable potential term and over reduce-then-join (dodges partial scoring, K^d blows up later). Correctness needs only admissibility; bound *tightness* is a later tuning follow-up (beam width absorbs looseness).

## Process + gotchas
- **`bungie-api-ts` const enums have NO runtime value** (ambient, erased by esbuild) — never use as runtime values; compare numeric literals with a comment (see `DestinyAmmunitionType` map, `itemType===20`).
- **Re-ingest** (`pnpm ingest --force`, only if a task changes the transform) needs `BUNGIE_API_KEY` in `.env`. **RAM-constrained machine** → `NODE_OPTIONS="--max-old-space-size=2048"`; check `free -h` before heavy installs. Slice 2a ran four full manifest fetches at 2048–2560MB with ~1–2GB free and never OOM'd.
- **One-off manifest inspection scripts** must live **inside the repo** (`scripts/*.ts`) so relative imports and the project tsconfig resolve, then be **deleted before committing** (verify with `git status --short`); write their reports to the scratchpad, never `data/`. Two more gotchas beyond the ones the plan pre-fixed: a bare `npx tsx` does **not** load `.env` (only `pnpm ingest` does — pass `--env-file-if-exists=.env` yourself), and this repo has no `"type": "module"`, so **top-level `await` is a transform error** — wrap in `main().catch(...)` like `scripts/ingest/run.ts`.
- **Alias:** `@/*` → `src/`; scripts use relative `../../src/lib/types`. `vitest.config.ts` maps `@`.
- **SDD workflow (for future phases):** implementers on a fast/cheap model when the brief carries full code; task reviewers mid-tier; final whole-branch review on the most-capable model. Progress ledger lives at `.superpowers/sdd/<plan-slug>/progress.md` (git-ignored scratch). **Slice 2a was executed inline by the controller instead** (no subagents) — that also works, and the per-task review still caught real defects; but note a task can be marked "complete, review clean" and still be **totally non-functional on real data** if its tests only exercise a fixture (see the slice-2a process lesson). Prefer a real-data floor assertion over a fixture-only green.
