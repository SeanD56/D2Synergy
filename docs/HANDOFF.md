## Phase 2 · SP3a — what shipped
Pure, DI'd `src/lib/solver/` module. `solve(build, ctx, options?) → SolveResult` where `ctx = { lookup, indexes }` (the existing `@/lib/types` dataset `Indexes` — NOT a new type), `options = { beamWidth?=16, topN?=5, statFit?, bound? }`. Unified **add-one-element beam search** over two open dimensions (subclass fragments + artifact perks): state = partial `Build`; a move adds one fragment (gated by the aspect-granted slot cap) or one artifact perk (gated by SP2 `canAddArtifactPerk`). States pruned by `state.priority` = **`synergyUpperBound`** (admissible optimistic bound, tie-break `priority || realized.score || key`); only **terminal (fully-filled)** states are completion candidates, ranked by realized `scoreSynergy.score + statFit`, top-N returned. `feasible=false` (empty builds) when pinned inputs admit no completion.

Key design points (verified in final review):
- **`synergyUpperBound` lives in `@/lib/synergy` (`bound.ts`), not the solver** — it co-varies with `scoreSynergy`'s weighting (which the seam hides), so the Phase-3 embedding layer stays drop-in. Solver reaches synergy ONLY via `scoreSynergy`/`getSynergies`/`synergyUpperBound`. Admissible per-keyword: `min(P,C)` links × triangular-rank × `ELEMENT_ALIGNED_MULT`, trigger cap, overlay clamped `Math.max(0,·)`. Independently verified to dominate the real (non-monotonic) scorer.
- **Prune key is the single admissible upper bound, NOT `realized + separate-gain`** — the split form is unsound because `scoreSynergy` is non-monotonic (a low-hash unaligned producer can steal a consumer from an aligned one).
- **Terminal-only routing is correct here because fill-to-cap is a HARD game floor** (Phase-1 decision: "fragments = max", "artifact tiers filled to slots" → underfilled builds are invalid deliverables). The admissible bound (computed fresh, not incrementally) still retains the path to the best *filled* build. **SP3b must revisit this if dynamic caps ever allow underfill.**
- **Acceptance gate (the point of the slice):** `tests/solver/beam.test.ts` delayed-reward test — a producer fragment (hash 200) whose only consumers are artifact perks survives the beam at W=1 with the bound ON (top build score 2, contains 200) and is pruned with a zero bound (top build 201, score 1.5). Proves the bound is load-bearing.

Parked follow-ups (non-blocking): tighten the bound for beam efficiency (measured vs real builds); revisit W=16 / topN=5 defaults; incrementalize per-successor recomputation in `makeState` (flagged in code for SP3b); DRY the key-comparator repeated across `beamSearch`/`solve`; author `CURATED_OVERLAY` entries (bound already guards negative weights).

## Phase 2 · SP3b slice-1 (weapons) — what shipped
Spec/plan: `docs/superpowers/specs/2026-07-24-phase2-sp3b-weapons-solver-design.md` · `docs/superpowers/plans/2026-07-24-phase2-sp3b-weapons-solver.md`.
Extends the SP3a beam **additively** (trailing default params → SP3a keys/behavior byte-identical) so it also selects, per open weapon slot, a **weapon + full roll** (one plug per unpinned column). Code: `src/lib/solver/weapons.ts` (`deriveWeaponPool` membership filter reusing validator `columnsFor`; `deriveWeaponSlotReach` reachable-union; `nonPowerAmmoInfeasible`), extended `candidates.ts` (`weapon`/`weaponPerk` candidate kinds + `WeaponPick`) and `beam.ts` (`SolverState.weapons`, staged expand, ammo eager-prune, terminal guard).
- **THE data finding (verified, load-bearing):** weapon plug hashes (`plugItemHash`) are a **disjoint namespace** from `perks.json` (0/112k resolve by hash), and `weapon.tags` is element-only. So a roll's synergy is recovered via a **plug-NAME bridge**: `Lookup.perkByName` + a name fallback in `collectBuildElements` (hash tried first, then name). Solver selects plugs by hash (move identity) but sets `{perkHash, perkName, column}` so synergy resolves by name. 149 plug names resolve uniquely, 0 ambiguous; a curated-resolution test (Voltshot→jolt, Incandescent→scorch, …) fails loudly on season drift.

## Decisions resolved (do not relitigate)
- **`feasible` means "the solver produced at least one completed build", NOT "the pinned inputs are satisfiable" (slice 4).** *Why:* beam search is incomplete, so the solver cannot prove unsatisfiability. `NO_COMPLETION_FOUND` is therefore a statement about the SEARCH; all seven other reason codes are proofs about the INPUTS. Keep that split visible in the type docs — collapsing it would let the solver overclaim.
- **Infeasibility causes ACCUMULATE rather than short-circuit (slice 4).** *Why:* a UI wants "fix these three things", and per-slot reporting means a build with two unsatisfiable weapon slots names both. `resolveSolverEnv` is the single source of truth; `buildSolverEnv` is a thin projection kept so beam-level callers and tests did not have to change.
- **Placeholder-plug exclusion is scoped to aspects/fragments ONLY (ingest repair).** *Why:* the discriminator (empty `itemTypeDisplayName`) was measured against those 205 plugs and nothing else. Mods have the same defect but an unmeasured discriminator, so extending it blindly could drop legitimate mods. A test pins the scope; measure first, then widen — that is slice 2c's job.
- **Aspect `classType` comes from the `plugCategoryIdentifier` prefix, not `item.classType` (ingest repair).** *Why, measured:* `item.classType` is `3` (Unknown) on all 81 aspect plugs, so the manifest field can never recover it, and aspect pools are class-specific.
- **The dynamic fragment cap does NOT break SP3a's terminal-only routing (aspect groundwork).** *Why:* `fragmentSlotsFor` grows monotonically as aspects are added, so a fragment added under a low cap is never invalidated and fill-to-cap stays satisfiable — underfill never becomes legal, so no best-partial tracking is needed. This closes a question the handoff had carried since SP3a.
- **The `Selection` refactor is a PREREQUISITE for slice 3, not its first task (user, 2026-07-28).** *Why:* doing it now migrates **two** dimensions instead of four, and keeps slice 3's whole-branch diff readable as "new dimension" rather than "new dimension mixed with a restructure". Slice 2b's byte-identical proof was tractable precisely because refactor and feature were separable.
- **That refactor runs as a DIRECT refactor + one whole-branch review — no brainstorm/spec/plan/SDD (user, 2026-07-28).** *Why:* zero behaviour change is intended, so the existing 229 tests **are** the spec; there is no design space to explore; and there is no dataset claim to be wrong about, which is the failure mode the heavier process exists to catch. The slice-2b `expand`-branch mutation proofs are the real safety net — they fail loudly if forwarding regresses.
- **That refactor covers BOTH the `Selection` object AND the `dimensionsAllDecided` terminal-guard factoring (user, 2026-07-28).** *Why:* both were flagged by the same review, both grow with every dimension slice 3 adds, and doing them together means one restructure and one review rather than two.
- **Slice 2b executes via SUBAGENT-DRIVEN development (user, 2026-07-27).** Slice 2a was run inline by the controller; 2b returns to SDD. Fresh subagent per task + review between tasks. Models per the SDD note below.
- **Slice 2b chooses ONLY the exotic armor piece, never the other four (user, 2026-07-27).** *Why, measured:* non-exotic armor is **2.17% tagged** (123/5681) vs **76.1%** for exotics (265/348), so a beam choosing the other four would search 5,681 items for almost no synergy signal while duplicating SP4. DIM's own writeup reports **77.7 trillion** combinations for a five-slot search and lists locking the exotic as a thing that *shrinks* it: <https://github.com/DestinyItemManager/DIM/wiki/Why-Loadout-Optimizer-is-slow-or-uses-a-lot-of-CPU>. `armor.pieces` is never written by the solver.
- **Guardian class becomes an EXPLICIT field, not derived (user, 2026-07-27).** `SubclassLoadout.classType?: Exclude<GuardianClass, "any">`. *Why:* deriving it from pinned aspects works today but evaporates in slice 3, which makes aspects solver-chosen while aspect pools are themselves class-specific. Typed `Exclude<..., "any">` because `"any"` matches no exotic and would surface as a silent `feasible: false`. Absent ⇒ the exotic dimension stays **closed**, which is what preserves SP3a/slice-1 byte-compatibility.
- **A `useExotic` pin is SUPPORTED, never REQUIRED (2026-07-27).** The user offered "requiring a pin is acceptable" as a simplification; it was declined because the dimension is only ≤47-branching after dedup (vs the 762-weapon dimension already shipped), so it buys nothing in cost while giving up "which exotic should I build around?". The offer is retained **unspent** as the pre-decided response if Task 5's measured cost is unacceptable — see Process + gotchas.
- **Mods get their OWN slice (2c) behind a capacity oracle (user, 2026-07-27).** *Why:* exact precedent — SP3a could only choose artifact perks because SP2 built the capacity oracle first. Mods are the same shape (flat selection under per-category capacity) and we lack the ingest data to model legality at all, so folding them into 2b would mean guessing a socket layout — the assumption class that produced slice 2a's 0/348 blocker.
- **Exotic class items: WANTED, but post-release, far down the line (user, 2026-07-27).** *Why:* (1) obtaining a desired two-spirit combination is an arduous random-roll farm most players will ignore, so full-pool optimisation spends complexity on recommendations most users cannot act on — this holds *even with* OAuth ownership data; (2) spirits are **partial mimics**, reproducing the original exotic's perk often without its full functionality. **Consequence — do NOT derive a spirit's tags from the mimicked exotic's text**; that would systematically over-state the effect. An honest model needs the spirit plug's own description or curated tags, and whether those plugs carry usable descriptions is **unmeasured** — check that first.

## Process + gotchas
- **⚠️ TESTING THE BEAM: a `beamSearch`-level test CANNOT catch a dropped state-forward — the search SELF-HEALS.** Discovered while proving slice 2b's forwarding invariant. If `expand` drops an already-decided dimension, `generateCandidates` simply re-offers that dimension's moves at the next level and the search re-picks it, so the final build looks correct while the state threading is broken. **Only a direct `expand()` test catches it** — build a state with the dimension already decided (so no candidate of that kind exists to mask the drop), call `expand`, and assert every child carries the decision. This generalises to every dimension slice 3 adds; reach for the direct-`expand` instrument, not an end-to-end one.
- **Mutation-proof recipe, and the trap in it:** back the file up to the **scratchpad** (not `/tmp`), apply the mutation, then **`grep` to confirm it actually applied** before interpreting the run — a `sed`/edit that silently matches nothing leaves the file intact and the test green, which reads *identically* to "the mutation didn't matter". Restore, then confirm `git diff` on the mutated file is empty.
- **`Math.max(...[])` is `-Infinity`** — any assertion of the form `expect(x).toBeGreaterThanOrEqual(Math.max(...list))` passes vacuously when `list` empties. Slice 2b's admissibility gate had exactly this shape; it now derives `list` from the state under test *and* asserts the expected membership separately. Watch for it in any new bound/property test.
- **`bungie-api-ts` const enums have NO runtime value** (ambient, erased by esbuild) — never use as runtime values; compare numeric literals with a comment (see `DestinyAmmunitionType` map, `itemType===20`).
- **Re-ingest** (`pnpm ingest --force`, only if a task changes the transform) needs `BUNGIE_API_KEY` in `.env`. **RAM-constrained machine** → `NODE_OPTIONS="--max-old-space-size=2048"`; check `free -h` before heavy installs. Slice 2a ran four full manifest fetches at 2048–2560MB with ~1–2GB free and never OOM'd.
- **One-off manifest inspection scripts** must live **inside the repo** (`scripts/*.ts`) so relative imports and the project tsconfig resolve, then be **deleted before committing** (verify with `git status --short`); write their reports to the scratchpad, never `data/`. Two more gotchas beyond the ones the plan pre-fixed: a bare `npx tsx` does **not** load `.env` (only `pnpm ingest` does — pass `--env-file-if-exists=.env` yourself), and this repo has no `"type": "module"`, so **top-level `await` is a transform error** — wrap in `main().catch(...)` like `scripts/ingest/run.ts`.
- **Alias:** `@/*` → `src/`; scripts use relative `../../src/lib/types`. `vitest.config.ts` maps `@`.
- **⚠️ SLICE 2B TASK ORDER WAS LOAD-BEARING — the lesson generalizes to 2c-4: measure cost right after the beam wiring, not at the end.** Task 5 measured real-data bound-call cost **immediately after** the Task 4 beam wiring, not at the end. *Why:* `exoticReach` contributes ~38 tagged elements to `addable` where a real build contributes exactly ONE exotic (~38× over-credit), and slice 2a proved inflated producer counts can blow the bound up 6× (11,190 → 66,071 calls) and break the cost tripwire. Measuring last would mean building Tasks 5-7 on an unverified cost assumption. The plan carried a **decision gate** (fallback: require a `useExotic` pin) that went **unspent** — measured cost came in at 5,567 calls, a 2.61x marginal factor, nowhere near the ~150,000 threshold. The feared ~38x never materialized: the beam pays per bound *call*, not per reach *element*.
- **Two slice-2b invariants an implementer might "clean up" and break:** (1) the existing weapons cost tripwire must still measure **exactly 10,527** bound calls (was 10,842 before the ingest repair — see the history table in the test) — that number is the proof this slice is additive, not merely non-breaking; (2) **every** `expand()` branch must forward `state.exoticHash`.
